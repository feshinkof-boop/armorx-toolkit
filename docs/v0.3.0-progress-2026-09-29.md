## Functionality added

* `armorx.capture` - offline capture inspection: hex dumps, raw byte streams and
  classic usbmon pcap, parsed by a built-in reader with **no packet-processing
  dependency**. Byte order is taken from the magic bytes, not assumed; unknown
  spans are reported with offsets; a corrupt frame is never re-flagged as a
  smaller valid one.
* `armorx.exchange` - shareable local envelope for configs and macros with schema
  version, provenance, device/firmware metadata and a SHA-256 content id over
  canonical JSON. Private identifiers are refused at construction.
* `armorx device doctor --bundle` - sanitised diagnostics file for issue reports.
* CLI: `capture inspect|formats`, `exchange export|inspect|verify|schema`.
* `pyproject.toml`: a `capture` extra that is deliberately empty, because the
  built-in reader needs nothing.

## Fixes

* `split_stream` now validates the family byte and the checksum instead of
  trusting the length byte (it could hand back bytes that `parse_frame` refused).
* `reassemble_a4` now reports a duplicate fragment index instead of overwriting.

bytes, corrupted checksums, invalid and duplicate fragment indexes, missing

## Static research progress

On `research/xbox-rt-threshold-2026-09-29`:

* **Mission 1 closed.** r4 provenance proven by CFG path analysis: the reaching
  definition is `0x1e0cd58 (r4 = sp + 1080 + 0xa)`, so the base is the candidate
  buffer plus `0x0a`. Per-channel arming state is stack-resident: base + index +
  {`0x76` previous, `0x78` mode, `0x7a` counter, `0x7c` armed}, two entries, index
  0 = LT and index 1 = RT.
* **LT gate `r8+0x1d6` and RT gate `r8+0x1db` folded into the artifacts.**
* **LT does reach equivalent logic**: LT and RT call the same helper `0x1e0a426`
  with different channel indices. The earlier "LT is only set to 0xff directly"
  statement is corrected.
* Mode byte domain documented as 0/1 with an explicit unknown; no initialiser was
  found on the entry-to-caller path, recorded as an inference.
* **Mission 2 answered.** Dominance cannot order the blocks: the container is a
  periodic loop, so `synthesis vs memcmp` and `r13 copy vs build14/build28` are
  all `CYCLIC_BOTH_ORDERS_POSSIBLE`. The earlier "sequential by dominance"
  population claim is **not reproducible** under block-index semantics and is
  corrected. Concrete paths exist both ways (synthesis -> memcmp 42 blocks,
  memcmp -> synthesis 105 blocks), and `sp+1080` - the memcmp operand - is the
  same buffer the synthesis writes.
* Three answers recorded: an analogue trigger movement **can** change internal
  state without emitting a frame (emission needs `b[r15+0x10]`, a memcmp
  difference, the tick gate and the repeat counter); the synthesis precedes the
  compared state on the concrete path; the **edge/toggle path is sufficient but
  not necessary**, because the analogue copy writes `candidate+0x0c/+0x0d` too.
* Research suite: **535 passed, 12 subtests, 0 failed**, including 10 new guard
  tests that pin the corrections.

6. No Windows application validation.
