# v0.3.0 interactive hardware validation

Status: **performed** on 2026-09-29 with the operator present, one popup per
physical action, each acknowledgement recorded in
`results/runtime/operator-actions/`. Machine-readable result:
`results/v0.3.0-interactive-validation-2026-09-29.json`.

Alerting was proven before any hardware work: the dialog was photographed on
screen while open, a critical notification bubble rendered as well, a sound was
played, and the first acknowledgements came back as machine-readable ACK records.
A click on the popup's DONE button was the acknowledgement; no chat confirmation
was required.

## Wire to evdev correlation

Correlation was done by timestamp, never by nearest frame.

* LT matched `ABS_Z` and RT matched `ABS_RZ` **exactly, sample for sample**, at the
  same timestamps.
* A, M1 and M2 matched their key events with the wire edge about 40 microseconds
  earlier, i.e. within one report interval.

This closes the long-standing discrepancy in which the input layer was believed
to show a smooth trigger ramp while the wire looked binary. Both show the same
coarse sequence: three rising samples within about 20 ms, then a hold, then two
falling samples within about 16 ms, for a pull the operator deliberately made
slowly over about two seconds. The quantisation is real and comes from the
device, not from the host.

## Power-state transition

* Off: `413d:2106`, Zikway "HID zk", one HID interface, `usbhid`, `hidraw2`
  created, **no input node**, no serial number.
* On: `045e:0b12`, Microsoft "Controller", three vendor-specific interfaces,
  `xpad` on interface 0, `js0` and `event18` present, serial exposed by sysfs.
* Same physical port `1-7` in both directions.
* The off-state report descriptor hashes to
  `f0e418decf688e7409ccebc1beb79a8d8c8c60e5c70150c5de7b056575bb366f`, **identical
  to the F20 receiver identity recorded earlier** - live confirmation that the
  identity is a power state and that the two units are indistinguishable from the
  wire.
* The switch back on needed two attempts: device 15 failed with two EPIPE
  descriptor reads, device 16 succeeded.
* While off, the vendor interface carried no payload traffic.

## The 32 to 48 byte question

**Not reproduced, recorded honestly.** A capture started 34 s before power-on and
ran for 340 s. All 76,382 type-0x20 reports were 48 bytes; not one 32-byte report
appeared. The first report was already the steady 48-byte form, 50 ms after
enumeration.

The earlier single observation of a 32-byte startup form that changes near 45.8 s
is therefore unsupported by this run. Do not repeat the 45.8 s figure as fact.
