# v0.3.0 interactive hardware validation checklist

Everything below needs a human physically present. Nothing here can be done
unattended, and none of it has been performed or claimed as passed.

Goal: make the later session short and deterministic. Each step is one action,
one capture, one artefact.

## Before starting

```bash
lsusb | grep -E "045E:0B12|413D:2106"          # note which personality is present
armorx device doctor                            # record the baseline
armorx device doctor --bundle results/hw-<date>-baseline.json
```

## Step 1 - power-state transition

1. With the unit attached and off (expect `413D:2106`), start a passive capture:
   `sudo -n tcpdump -i usbmon<N> -w transition.pcap`
2. Press the power button once, do nothing else, wait 10 s.
3. Stop the capture and run `armorx capture inspect transition.pcap --summary`.
4. Expect a re-enumeration to `045E:0B12` on the same port. Record both
   identities, the timestamps and whether the vendor interface carried any
   payload before the transition.

## Step 2 - early enumeration and the 32 -> 48 transition

1. Power the unit off, then start the capture **before** powering it on.
2. Power it on and leave it alone for 3 minutes.
3. Record: first GIP timestamp, last 32-byte timestamp, first 48-byte timestamp,
   the delta, the sequence numbers around the change, and any traffic in the
   second before it.
4. Do not assume 45.8 s: the previous observation is a single sample.

## Step 3 - one control at a time

For each of LT, RT, A, M1 and M2: idle 5 s, press or sweep once, release, idle
5 s, with the capture running the whole time. Between controls, stop and label
the capture.

For LT and RT use a slow sweep, about two seconds of travel, and note whether the
input layer ramps while the wire value is binary - this is the open discrepancy
recorded in `results/firmware/d2-emission-ordering.json`.

## Step 4 - what to verify afterwards

* `armorx gip decode` on a saved report reproduces the earlier field map.
* `armorx capture inspect` finds no phantom frames in any new capture.
* The RT digital question: whether a fully analogue RT change alone ever produces
  a D2 report.

## Do not do

* No configuration writes, no DPI/lighting/macro writes, no firmware operations.
* No Bluetooth pairing.
* No macro or OTA traffic replay.
