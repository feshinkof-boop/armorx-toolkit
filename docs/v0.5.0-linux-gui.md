# v0.5.0 Linux desktop GUI

Status: development on dev/v0.5.0-linux-gui.

Issue: #4 — desktop GUI for configuration and macro editing.

Install from a development checkout:

    python -m pip install -e ".[gui,dev]"
    armorx-gui

## Milestone 1 — shell and editor

- BLE scan and live D6 read through the released armorx.live backend.
- Open JSON / 144-byte binary configs offline.
- Model / firmware / battery, length and CRC display.
- M1-M4 remapping.
- First trigger, stick, sensor and turbo controls.
- Automatic CRC regeneration.
- Exact byte-level diff table using armorx.diff.
- Reset and validated JSON/bin export.
- Qt-independent GuiConfigSession model.

## Milestone 2 — native Apply / Verify / Rollback and profiles

The desktop now wires write buttons directly to the released v0.4 backend:

    GUI Apply & Verify
      -> armorx.gui_workflow.apply_target
      -> armorx.live.apply_config

    GUI Rollback
      -> armorx.gui_workflow.rollback_backup
      -> armorx.live.rollback_config

There is still only one D6/D7/0E implementation.

Apply & Verify uses a timestamped automatic backup, worker-thread BLE I/O, a
native Qt confirmation dialog on the main thread, the backend exact diff and
unknown-byte refusal, one D7 transaction, one persistence command and two D6
read-backs. It never automatically retries a partial write.

The GUI intentionally does not expose the CLI advanced allow-unknown-diff
escape hatch.

Rollback last backup invokes the released rollback backend. It restores the
exact saved .bin bytes and keeps unrelated-state refusal. The GUI does not
expose the CLI unrelated-state override.

Local profiles live under the XDG application data directory. They are full
validated 144-byte images and record only safe metadata (model, firmware and
optional note), never BLE address, hostname or serial. Loading a profile is
offline until the operator explicitly presses Apply & Verify.

QtConfirmationBridge lets a BLE worker call the backend synchronous
confirmation hook while the actual QMessageBox is created on the Qt main
thread.

Hardware-free tests cover profile integrity/privacy, backup collision handling,
accepted apply, declined apply with zero mutating frames, session-record
creation and exact-byte rollback.

The package version remains 0.4.0 until the v0.5 GUI itself has been supervised
on real hardware.

## Milestone 3 — visual sticks, deadzones and recovered curve bytes

The GUI now adds dedicated **Stick visuals** and **Trigger visuals** tabs.

For each stick it shows:
- center/side deadzone raw-byte controls and a ring preview;
- the six recovered curve bytes (mode, YDivx, point-1 X/Y, point-2 X/Y);
- a theme-aware control-point preview.

For each trigger it shows the recovered center/side deadzone bytes with a ring
preview. All controls remain bound to the exact named offsets already present in
armorx.config, regenerate CRC through GuiConfigSession, and preserve every
unknown byte.

The visualizations are intentionally evidence-bounded: they are normalized
0..255 **byte-space previews**. They do not claim that a byte value is a physical
percentage or that the plotted curve is the firmware's exact transfer function.
That scaling/math remains unresolved research.

The original numeric controls remain under **Advanced bytes** and are
synchronized with the visual editors.

## Milestone 4 — offline macro timeline editor

The **Macros** tab is built directly on `armorx.macro` and the captured V41
portable macro JSON model. It provides:

- macro name;
- M1-M4 trigger selection;
- long-press, tap, long-press-cycle and tap-cycle modes;
- repeat time and in-use flag;
- a 1..16 step timeline;
- chords such as `B+RT`;
- per-step hold and interval times;
- add/remove/reorder controls;
- live validation and decoded JSON preview;
- import/export of validated macro objects.

The editor is deliberately **offline only**. Opening, editing and exporting a
macro does not use BLE and does not call the community/network API. Unknown keys
such as Share/Screenshot remain rejected instead of guessed; joystick
pseudo-keys keep the evidence level documented by `armorx.macro`.
