Supervised session with the operator present. **Read-only**: no D7, no 0E, no
`allow_mutating`, no configuration change, no frame replay. The only
application-protocol request sent was the proven non-mutating D6 configuration
read, plus standard GATT identity reads.

BLE addresses appear only in local runtime artefacts. They are **not** in this
document, in the repository, in the JSON companion or in the pull request.

An independent read-only enumeration (no writes, no subscriptions) confirms
exactly what the toolkit reports:

* the service `00000000-0000-1000-8000-00805f9b34fb` is **genuinely advertised**
  at handle 115 - it is unusual, but it is not a decode artefact;
* `FFE1` = `0000ffe1-...` handle 116, properties `write-without-response` and
  `write`;
* `FFE2` = `0000ffe2-...` handle 118, properties `read` and `notify`, with a
  `2902` client-characteristic-configuration descriptor;
* other services present: `180F` Battery, `1800` GAP, `AE00` vendor
  (`AE01` write, `AE02` notify) and `180A` Device Information.

Observation, not an error: the ATT handles read one lower than the values
recorded in the 2026-09-26 session (116/118 versus 117/119); the UUIDs,
properties and descriptors are unchanged.

## Comparison with the research implementation

`ble/real-device/armorx_real.py` (read-only phase) as an independent reference:

| item | research client | toolkit | same |
| --- | --- | --- | --- |
| FFE1 / FFE2 UUIDs | as above | as above | yes |
| D6 request bytes | `A5 04 D6 7F` | `A5 04 D6 7F` | yes |
| fragment count | 10 | 10 | yes |
| fragment indexes | 1..10 | 1..10 | yes |
| reassembled length | 144 | 144 | yes |
| declared length | `0090` | `0090` | yes |
| stored CRC | `2c40` | `0x2C40` | yes |
| image bytes | `bdef9c61...b895beb6` | `bdef9c61...b895beb6` | **byte-identical, 0 of 144 offsets differ** |

The image comparison is against the research client's own saved output from the
2026-09-27 physical sessions, because the live rerun today **failed to establish
a link**: three LE create-connection attempts on the lab dongle returned
`COMMAND_DISALLOWED_ERROR` after the advertisement was seen. Adapter ownership
was restored automatically, and the attempt was not repeated further, since the
stored output already provides the byte-level comparison this validation asks
for.

Two implementation differences are worth recording. The research client
concatenates fragments in **arrival order**; the toolkit reassembles **by
fragment index** and refuses conflicting duplicates. And the research client
sends `0B`, `EF`, `D4` and `E2` before `D6`, whereas the toolkit sends `D6`
alone and still received all ten fragments with a valid image, so the preamble
is not required for a D6 read.

## Defect found and fixed

**Read-config and backup proved the 144-byte image but recorded nothing about
the fragments it was reassembled from.** The brief for this session asked
exactly for that accounting, and it was genuinely absent.

* `read_config` now accepts a report dict and fills it with the fragment count
  and, per fragment, the index, frame size, data size and checksum status;
* `armorx live read-config` and `armorx live backup` both carry it;
* four hardware-free regression tests cover it, including the CLI payload;
* validated afterwards on the real device: 10 fragments, indexes 1..10,
  15 data bytes each except 9 for the last, all checksums valid, and the image
  still hashes to the same SHA-256.

No test was weakened and no proven protocol behaviour was changed.

## The exact gate before any D7 testing

1. Save the live baseline as read today.
2. D7 the **byte-identical** image only - a no-op round trip.
3. Issue `0E` persistence.
4. D6 read back and require an exact byte and SHA-256 match against the baseline.
5. Only after that passes may a real configuration mutation be exposed.

Nothing in this session crossed that gate.
