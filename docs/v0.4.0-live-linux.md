# v0.4.0 live Linux development

Status: **development branch only** — `dev/v0.4.0-live-linux`.

v0.3.0 remains the latest released toolkit.  The package version intentionally
stays at 0.3.0 until the live backend has been validated on real Linux BLE
hardware.

## Goal

Make normal ARMOR-X configuration usable from Linux without duplicating the
protocol model already validated in the project.

The target safety flow for a future public write command is:

1. connect through the proven BLE FFE1/FFE2 path;
2. D6-read the current 144-byte image;
3. verify length and CRC;
4. save a privacy-conscious baseline backup;
5. calculate and show the exact byte diff;
6. only after explicit user confirmation, D7 the complete validated image;
7. issue `A5 05 0E 00 B8` to persist;
8. D6-read again and require byte-for-byte equality.

No raw-opcode console is planned for the public CLI.

## Proven transport basis

From the existing Android/Windows captures:

- service: `00000000-0000-1000-8000-00805f9b34fb`;
- FFE1: WriteWithoutResponse;
- FFE2: Notify;
- D6: payload-free request, ten indexed A4 fragments, 144 bytes total;
- D7: ten A4 fragments carrying the complete 144-byte image;
- D7 acknowledgement observed as `A5 05 D7 00 81`, but not for every captured
  image, so one-ack-per-write is not treated as a contract;
- D7 changes live/volatile configuration;
- `A5 05 0E 00 B8` persists the D7-written configuration across power loss on
  the tested ARMOR-X Pro.

## Milestone 1 implemented

The first v0.4.0 commit deliberately exposes only non-mutating operations:

```text
armorx live scan
armorx live info --address <BLE address>
armorx live read-config --address <BLE address>
armorx live backup --address <BLE address> -o baseline.json
armorx live plan baseline.json target.json
```

Install the optional backend with:

```bash
python -m pip install -e ".[live]"
```

The module uses Bleak lazily, so the normal toolkit still has no mandatory BLE
dependency.

Mutating D7/0E helpers exist only behind an explicit `allow_mutating` transport
gate for mock testing.  **No public CLI command enables that gate in this
milestone.**

## Write-safety gate (validated 2026-09-29)

The only write path in the public CLI is a supervised byte-identical no-op:

```
armorx live validate-write-gate --address <BLE address> \
    --backup-prefix <path prefix> [--authorized]
```

It takes **no** target image, opcode or payload: the bytes it writes are the
bytes it read from the device immediately before the write. It reads the live
144-byte config twice, requires the two reads to be identical, validates the
length and CRC, writes the pre-write baseline (`.json`, `.bin`, `.sha256`)
before anything else, and refuses to continue unless `--authorized` is passed,
which is done only after the operator acknowledged a desktop dialog with an
audible alert. It then writes the image as ten D7 A4 fragments, records any D7
acknowledgement (an absent acknowledgement is recorded as an absence, never as a
rejection), sends the persistence frame once, and verifies the result with two
further D6 reads requiring an exact byte-for-byte and SHA-256 match.

Still deliberately absent: `live apply`, `live write-config`, a raw opcode
console, and any command that accepts a caller-supplied image. The first
supervised run passed byte-for-byte with zero differing offsets — see
`docs/v0.4.0-noop-d7-validation-2026-09-29.md`.

## Next validation gate

With the operator present:

1. run `live scan` and confirm the ARMOR-X advertisement;
2. run `live info` and compare model/firmware/battery to the known values;
3. run `live read-config` and compare the D6 image to the established research
   harness;
4. run `live backup` and privacy-scan the saved file;
5. compare repeated D6 reads for stability.

Only after those read-path checks pass should a no-op, byte-identical D7 round
trip be promoted into an explicit supervised experiment.  A general `live
apply` command comes later, after that gate is proven.
