# v0.4.0 live Linux BLE support

Status: **release-ready v0.4.0**. The Linux live path was validated against a
real ARMOR-X Pro on 2026-09-29. The Windows application remains a separate
v0.2.1 deliverable.

## What v0.4.0 adds

The optional Bleak backend exposes:

```text
armorx live scan
armorx live info --address <BLE address>
armorx live read-config --address <BLE address>
armorx live backup --address <BLE address> -o baseline.json
armorx live plan baseline.json target.json
armorx live apply target.json --address <BLE address>
armorx live rollback <backup-prefix> --address <BLE address>
```

Install the optional backend with:

```bash
python -m pip install -e ".[live]"
```

or install the tagged source with the `live` extra.

## Proven transport basis

The tested device advertises the vendor BLE path used by the existing research:

- service `00000000-0000-1000-8000-00805f9b34fb`;
- FFE1 for Write / WriteWithoutResponse;
- FFE2 for Notify;
- D6: payload-free request, ten indexed A4 fragments, 144 bytes total;
- D7: ten A4 fragments carrying the complete 144-byte image;
- D7 acknowledgement observed as `A5 05 D7 00 81`;
- `A5 05 0E 00 B8` persists a D7-written configuration on the tested
  ARMOR-X Pro.

One acknowledgement pattern is evidence from the tested hardware, not a
requirement that every firmware revision must emit exactly one acknowledgement.

## Public write safety model

`armorx live apply`:

1. validates the target before touching BLE;
2. reads the live configuration twice and refuses if the reads differ;
3. validates 144 bytes / declared length / CRC;
4. automatically writes and reopens a privacy-conscious backup;
5. records every changed byte and decoded field;
6. refuses changes to undecoded bytes by default;
7. asks the operator to confirm the exact plan;
8. sends one full-image D7 transaction;
9. sends the persistence command once;
10. requires two exact D6 read-backs matching the target.

`armorx live rollback` validates the backup trio and writes the exact saved
`.bin` bytes; it does not rebuild the image from decoded fields. It refuses an
unrelated live state by default.

There is no public raw-opcode or arbitrary-payload console.

## Hardware validation

The development sequence closed four progressively stronger gates:

- read path: repeated D6 reads, fragment accounting, CRC and backup privacy;
- byte-identical no-op D7 + 0E + double-D6 verification;
- supervised M1 B→A mutation, physical wire proof, persistence and exact restore;
- final public `apply` / `rollback` validation, including a second fixed
  apply→rollback pair with no override.

The public M1 B→A test changed exactly offsets 0, 1 and 135 (CRC bytes plus
`mapKeys[23]`), produced A on the USB GIP wire, survived a power cycle, then
returned to the exact original SHA after public rollback and another power
cycle.

## Experimental validation commands

`armorx live validate-write-gate` and
`armorx live validate-reversible-m1` remain available for reproducibility and
are explicitly experimental. Normal users should use `read-config`,
`backup`, `apply`, and `rollback`.
