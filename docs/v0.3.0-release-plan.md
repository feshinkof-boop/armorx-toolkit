# v0.3.0 release plan

Status: **released** as `v0.3.0` on 2026-09-29. PR #8 was merged into `main`.
The release tag points to merge commit `4e055c39d143b33b305a2e1a6cfa75ed2792f7b8`,
and the public release publishes the wheel, sdist, source ZIP and SHA-256
checksum manifest.

This document uses the project evidence levels **proven**, **strong evidence**
and **unknown**. Unknown research questions are not promoted into public API
claims.

## 1. Release scope

v0.3.0 is the Python/Linux/offline toolkit release. The public package includes:

1. `armorx.protocol` — A5/A4 framing, checksum validation, fragmentation,
   index-keyed reassembly, opcode evidence metadata and stream splitting.
2. `armorx.gip` — offline parsing of observed Xbox type-`0x20` reports with
   proven A, M1, M2, LT and RT fields and unknown bytes retained.
3. `armorx.device` — read-only Linux sysfs discovery, identity classification,
   xpad-aware diagnostics and privacy-sanitized issue bundles.
4. `armorx.transport` — transport abstractions, scripted mocks and a read-only
   hidraw seam that refuses writes.
5. `armorx.capture` — offline hex/raw/classic-usbmon-PCAP inspection without a
   mandatory packet-processing dependency.
6. `armorx.exchange` — versioned config/macro exchange envelopes with canonical
   JSON validation and deterministic SHA-256 content IDs.
7. CLI groups for `device`, `protocol`, `gip`, `capture` and `exchange`
   alongside the existing config/macro/community commands.

The latest public Windows configurator remains **v0.2.1**. v0.3.0 does not
replace or re-version the Windows executable.

## 2. Safety boundary

The v0.3.0 public toolkit is read-only with respect to attached devices. It does
not expose configuration writes, macro writes, DPI/lighting writes, arbitrary
HID output, OTA or firmware flashing. Firmware disassembly, raw private captures
and researcher-only experiment tooling remain outside the public package.

## 3. Real-hardware validation completed on 2026-09-29

The release candidate was validated against an ARMOR-X Pro directly connected
over USB:

- `045e:0b12` <-> `413d:2106` was observed live on the same physical USB
  port during power-state transitions.
- The off-state `413d:2106` personality exposed one HID interface, `usbhid`,
  a hidraw node, no input node and no serial number.
- The on-state `045e:0b12` personality exposed three vendor-specific
  interfaces, with `xpad` on interface 0 and Linux input nodes present.
- LT and RT wire values matched `ABS_Z` / `ABS_RZ` sample-for-sample by
  timestamp.
- A, M1 and M2 matched the documented wire bits and Linux key events.
- The capture parser matched an independent parser across the supervised
  captures and produced no phantom A5 frames after the regression fix.
- The diagnostics bundle was generated on the real host and privacy-scanned.

## 4. Historical 32-byte report correction

A previous research snapshot described a 32-byte type-`0x20` report as a
"startup form" that changed to 48 bytes near 45.8 seconds. That behavior was not
reproduced in the controlled release-validation run.

A capture started 34 seconds before power-on and ran for 340 seconds. All
**76,382** observed type-`0x20` reports were 48 bytes, with the first report
arriving about 50 ms after enumeration. Therefore:

- the parser may retain compatibility with the previously observed 32-byte form;
- v0.3.0 does **not** claim that 32 bytes is a startup form;
- the existence, trigger and role of that form remain **unknown**;
- the historical 45.8-second figure must not be presented as a general fact.

## 6. Non-blocking unknowns

These remain explicit research questions and do not block this release:

- stick signedness/scaling until a stick sweep is correlated to evdev;
- existence and role of the previously observed 32-byte report form;
- cause of the coarse trigger quantisation;
- vendor-personality payload behavior beyond the observed silent periods;
- D-pad, View, Menu, Guide, L3/R3 and Capture live confirmation;
- internal firmware-only state such as the `0x1e0a426` mode byte,
  `[r15+0x1d0]` and `[r15+0x25]`;
- Windows GUI validation, because the Windows application remains a separate
  v0.2.1 release line.

## 7. Compatibility and release artifacts

- Python requirement remains **3.10+**.
- Existing config, macro and community commands retain their behavior.
- No new mandatory runtime dependency is introduced.
- Release assets should include the Python wheel, sdist, source ZIP and SHA-256
  checksum manifest.
- Release tag: `v0.3.0`.
- The v0.3.0 tag must point to the merged release-candidate commit on `main`.

## 8. Post-release follow-up

Future work should focus on the non-blocking unknowns above, PCAPNG support,
additional live control mappings, and continued Linux/userspace-driver research.
Those items belong to a later release and must not delay v0.3.0.
