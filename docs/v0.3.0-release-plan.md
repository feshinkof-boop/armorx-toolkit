# v0.3.0 release plan (offline foundation)

Status: work in progress on `dev/v0.3.0-offline-2026-09-29`. No tag, no
published release, no merge to `main` has been made.

This plan is derived from the repository as it stands, not from a wishlist.
Every claim below is tagged with the evidence level the toolkit uses:
**proven**, **strong evidence** or **unknown**.

## 1. What the public package does today

`armorx-toolkit` 0.2.0 ships one CLI with three groups:

```text
armorx config    decode | validate | keys | map | patch | create | configjson
armorx macro     build | validate | inspect | keys
armorx community list | import-code
```

The Python surface is `armorx.config` (144-byte configuration image, CRC-16
over bytes 2.., key mapping, canonicalisation), `armorx.macro` (macro DSL and
macro JSON) and `armorx.community` (reproduced client request shapes). All of
it is offline; nothing in the package transmits to a device.

## 2. Proven research that can become public functionality without hardware

| Research finding | Evidence | Public form it can take |
| --- | --- | --- |
| `A5 \| length \| opcode \| data… \| checksum`, checksum is sum-mod-256 | proven | frame build/parse library |
| `A4 \| length \| opcode \| fragment_index \| ≤15 data \| checksum`, ten fragments, 9×15+9 = 144, fragments may be interleaved | proven | fragment reassembly keyed by index |
| D6 is the payload-free full configuration read; reply is ten A4 fragments | proven | offline decode of a saved D6 exchange |
| D7 writes the whole 144-byte image as ten A4 fragments | proven | offline validation of a D7 payload |
| `A5 05 D2 01 7D` enables and `A5 05 D2 00 7C` disables the raw input stream | proven | opcode description only; the toolkit does not transmit |
| `A5 04 0B B4` sanity query, `A5 05 0B 30 E5` reply | proven | fixture and opcode description |
| Vendor HID personality `413D:2106`, usage page `0xFF7A`, 64-byte interrupt endpoints | proven | device recognition and diagnostics |
| Xbox personality `045E:0B12`, xpad binds interface 0 | proven | device recognition, xpad-aware diagnostics |
| GIP type-0x20 input fields: A byte 4 bit 0x10, M1 byte 4 bit 0x20, M2 byte 5 bit 0x40, LT bytes 6-7, RT bytes 8-9, left stick 10-13, right stick 14-17 | proven | offline GIP parser |
| Startup 32-byte and steady-state 48-byte report forms | proven | parser supports both |
| RT has no digital bit in the Xbox report; the device synthesises one | proven | documented, never fabricated in the parser |

## 3. Research that must stay researcher-only

* Firmware addresses, disassembly, `rom.lst` validation and q32s tooling: they
  belong in the research tree, not in a distributed package.
* Raw BLE/ADB captures and `btsnoop` logs, which contain device identifiers.
* Anything that performs writes: D7 configuration writes, D8 macro writes, DPI
  and lighting writes, RCSP, OTA, firmware or bootloader operations. The
  research harness gated these behind explicit experiment scripts and they stay
  there.
* Speculative interpretations of unresolved firmware behaviour.

## 4. Scope of v0.3.0

In scope:

1. `armorx.protocol` - framing, checksum, fragment reassembly, opcode table.
2. `armorx.gip` - offline GIP input parser.
3. `armorx.device` - read-only discovery, classification, `doctor`.
4. `armorx.transport` - transport seam plus mock and read-only hidraw.
5. CLI groups `device`, `protocol`, `gip`.
6. Offline capture inspection for byte streams (already possible through
   `protocol decode --stream`; PCAP support stays optional).
7. Documentation and fixtures that let contributors work without hardware.

Explicit non-goals:

* No Linux kernel driver and no userspace driver daemon.
* No transmission, no pairing, no configuration writes.
* No claim of hardware validation for anything added in this release.
* No community backend deployment; schema and serialisation work only if it
  directly serves local import/export.

## 5. Hardware-dependent blockers

| Blocker | Why it blocks | What is needed |
| --- | --- | --- |
| `413D:2106` vs `045E:0B12` identity transitions were only observed with hardware | recognition is implemented, but the transition cannot be reproduced offline | ARMORX Pro + USB cable |
| Vendor-report payload semantics | the vendor interface produced no payload-bearing frames in any capture | the companion app driving a known configuration action |
| GIP 32→48 transition cause | unknown; only observed | a capture from the first minute after enumeration, repeatedly |
| RT digital synthesis on the wire | proven statically, not observed end to end | device plus a live RT sweep |
| Windows application validation | no VM or Wine available | a disposable Windows environment |

## 6. Release acceptance criteria

Status as of 2026-09-29 (see `docs/v0.3.0-hardware-validation-2026-09-29.md`):

| # | criterion | status |
| --- | --- | --- |
| 1 | full suite passes without hardware | satisfied (184 tests, 0 skipped) |
| 2 | every group has working `--help` | satisfied |
| 3 | `device doctor` exits 0 with a clear no-device result | satisfied, and validated with a real device present |
| 4 | malformed input gives a specific error and exit code 2 | satisfied |
| 5 | no command opens a device for writing | satisfied by inspection and by the live session: no agent-initiated writes |
| 6 | every protocol statement carries an evidence level | satisfied |
| 7 | research tree untouched | satisfied |
| 8 | discovery, doctor and the capture parser validated on real hardware | satisfied on 2026-09-29 for the Xbox personality; the vendor personality was not re-observed |
| 9 | interactive controls validated | **not satisfied**, human required (see the interactive checklist) |

Original criteria list follows.

1. The full public test suite passes on a machine with no ARMORX hardware.
2. `armorx --help` lists every group; each group has working `--help`.
3. `armorx device doctor` returns exit code 0 with a clear "no device" result
   when nothing is plugged in.
4. Every parser refuses malformed input with a specific message and exit code 2.
5. No command in the package opens a device for writing.
6. Every documented protocol statement carries an evidence level.
7. The research tree is untouched and remains readable as evidence.

## 7. Compatibility

* Python 3.10+ is preserved; no new mandatory dependency is introduced.
* Existing `config`, `macro` and `community` commands keep their behaviour and
  output shape.
* The package version stays at 0.2.0 on this branch until the code is coherent
  and tested; the intended bump is 0.3.0 and is documented in the changelog
  under "Unreleased".

## 8. Test strategy

* Unit tests per module, all hardware-free.
* A synthetic sysfs tree for discovery: two recognized identities, an unknown
  identity, driver symlinks, a hidraw node and an input node.
* Synthetic GIP frames built from the documented layout - marked synthetic in
  the test module, never passed off as captures.
* Malformed-input tests for every parser: bad checksum, bad length, bad family,
  missing fragments, mixed-opcode fragments, short frames, wrong type byte.
* CLI tests covering exit codes, JSON shape and no-device behaviour.
* A skip is only acceptable for tests that inherently require hardware or an
  unavailable optional toolchain, and the reason must be stated in the marker.

| Wire to evdev correlation method | CLOSED | timestamp correlation used throughout, never nearest frame |
| The 32-byte starting report form | NON-BLOCKING UNKNOWN | did not occur in a 340 s capture that began before power-on; the product works in the observed steady form, and the earlier observation is not relied on |
| Stick signedness and scaling | NON-BLOCKING UNKNOWN | the decoder now claims neither; a stick sweep is the missing input |
| Trigger quantisation cause | NON-BLOCKING UNKNOWN | the wire values and their timing are recorded, the internal cause is not |
| `0x1e0a426` internal mode byte, `r15+0x1d0`, `r15+0x25` | NON-BLOCKING UNKNOWN | internal firmware state, not needed by any shipped feature |
| Vendor-personality payload question | NON-BLOCKING UNKNOWN | the `hidraw` node is root-only on a stock install, so it was not read; no shipped feature depends on it |
| D-pad, View, Menu, Guide, L3/R3, Capture | NON-BLOCKING UNKNOWN | not exercised; the decode path is shared with the buttons that were validated |
| Windows application validation | NON-BLOCKING UNKNOWN | out of scope for the Python toolkit release |

No blocker in this release remains classified BLOCKING. The version is bumped to
0.3.0 on the development branch only; the tag, the release and the merge are
deliberately still not done.
