# v0.3.0 hardware validation, 2026-09-29

Read-only session. No configuration write, no HID output, no Bluetooth, no power
cycle, no firmware operation, and no popup asking the user for anything. The
device was already attached and powered when the session started.

The device stayed in this personality for the whole session and did not shut
down, so the vendor-personality case (`413D:2106`) was not re-observed today.

## Device discovery validation

`armorx device list` found 6 devices and classified exactly one as supported.
Compared with raw sysfs and `lsusb`, the toolkit agrees on VID, PID, path,
speeds and drivers. Real hardware exposed two bugs, both fixed with regression
tests:

1. every interface of a multi-interface device was reported as number 1, because
   the number was read from before the dot in `<dev>:<cfg>.<iface>`;
2. the sysfs serial was printed as a hex dump (`3039373130373639...`) instead of
   the serial the device actually reports (`09710769957143`).

`armorx device inspect 1-7` now reports interfaces 0, 1 and 2 with their correct
classes and drivers, and the decoded serial.

## Doctor validation

`armorx device doctor` returned `ok: true` with `blocking_checks: []` and one
finding, `hidraw_permissions`, which is accurate: neither hidraw node is readable
by this user and neither belongs to the ARMORX device. Before this session that
finding forced `ok: false`, which was misleading because none of the read-only
paths need hidraw. Findings and blocking checks are now reported separately.

## 32 -> 48 transition result

**Not reproduced or refined, and the reason is evidence-based**: the device had
already been enumerated for about 98 seconds when the first capture started, and
the steam was already in the 48-byte steady form from the first record. Nothing
32-byte was present in any capture today. The earlier observation placed the
switchover near 46 s after enumeration; refining it needs a capture that starts
within seconds of enumeration, which requires a power cycle or a re-cable, and
both were out of scope for this session. The transition cause remains UNKNOWN.

## Capture parser validation

`armorx capture inspect` was compared against an independent parser written for
this session: both report 62,702 records, 30,009 GIP reports, 48-byte lengths and
255 distinct sequences.

The comparison also exposed a real parser defect. In eight records the GIP
sequence byte happened to be `0xA5` and the surrounding report bytes happened to
satisfy the family and checksum test, so the toolkit reported eight phantom A5
frames. Payloads recognised as GIP input reports are now decoded as GIP only, and
the capture reports zero frames. A regression test builds exactly such a report
and asserts that no frame is extracted.

Other traffic observed and left as UNKNOWN: 7-byte payloads on the interrupt IN
endpoint (490 records, prefixes `02 00 ff` and `02 00 00`), 4-byte payloads (450),
and bulk-ish 98/106/240-byte payloads on endpoint `0x84` (interface 2) that
contain `0xA5` bytes without forming valid frames. No semantics are claimed.

## Limitations

* No vendor-personality observation today; the earlier `413D:2106` findings stand
  unvalidated by this session.
* No interactive controls were exercised: LT, RT, buttons, M1/M2 and power-button
  behaviour still need a user-assisted session (see the interactive checklist).
* The 32 -> 48 transition and the counter semantics remain unknown.
* All the live work was passive; the only writes on the bus were xpad's own
  initialisation traffic, which is automatic kernel behaviour and not
  agent-initiated.
