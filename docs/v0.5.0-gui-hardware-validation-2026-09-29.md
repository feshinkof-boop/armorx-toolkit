# v0.5.0 Linux desktop configurator — supervised hardware validation (2026-09-29)

First real-hardware run of the **PySide6 GUI path** (`armorx-gui`), not the CLI.
Every read and write below travelled through the GUI's own worker path:

```
ArmorXWindow button  ->  armorx.gui_workflow  ->  armorx.live.apply_config / rollback_config
```

The GUI contains no protocol or write implementation of its own; it delegates to
the released v0.4.0 backend and its safety contract (D6 x2, backup, diff,
confirmation, D7, 0E, D6 x2 verify).

## Result

**GUI HARDWARE VALIDATION: PASS** — the device finished on its exact original
configuration, byte-for-byte, after a final power cycle.

## Bug found and fixed (Phase 18)

**`GUI-BUSY-001` — a completed background task could leave the window stuck on
"busy".** `_task()` started an `AsyncTask` (a `QRunnable`) without keeping a
reference. `QThreadPool` drops its reference as soon as `run()` returns, so the
task - and its `TaskSignals` object - could be collected while its `result` /
`finished` signals were still queued. When that happened the result never reached
the window (scan table empty) or the `finished` delivery was lost, leaving
`_busy` true: the progress indicator never hid and **every** action button stayed
disabled - a fresh window could not scan, read, or apply at all.

Reproduced hardware-free (offscreen Qt): the worker result never arrived and
`_busy` stayed true. Fixed by keeping a strong reference to the runnable until
its `finished` signal has been delivered (`self._tasks` + `_finish_task`), which
is the only change to `src/armorx/gui.py` in this session. Three regression tests
in `tests/test_gui_window.py` fail on the old code and pass on the new one.

No second write implementation was added and the v0.4 backend safety contract was
not weakened.

## Tooling note (not a product defect)

The first passive USB capture died at 08:29 because it had been started from an
ad-hoc analysis cell that was later killed on its 5-minute timeout.

The first M1 request then hit its own bound: its requester exited `TIMEOUT` after
1800 s while the popup window itself stayed on screen, and the operator's click a
few minutes later wrote the ack file with no requester left listening. That press
was therefore never observed by the session (the capture was already dead, and the
request was past its own timeout).

A second, single M1 press was requested once the capture had been restarted as a
tracked background process; that press was recorded and is the physical evidence
in this report. The unreachable first window is recorded as a timeout, not as an
action that happened.
