# Public `live apply` / `live rollback` — hardware validation, 2026-09-29

Branch: `dev/v0.4.0-live-linux` (development, not released). This session ran the
**public** commands against a real ARMOR-X over Linux BLE. The experimental
`validate-reversible-m1` and `validate-write-gate` commands were not used to
perform any mutation.

Machine-readable evidence: `results/v0.4.0-public-apply-validation-2026-09-29.json`.

## Device

Model `ZJ-XT`, firmware `2741`, battery 97–98 %. The advertisement arrived
without a local name on every adapter used, so the conservative classifier
reported `is_armorx: false` and the device was identified by the locally recorded
address plus its `ZJ-XT` manufacturer payload — never by a guess.

## Baseline

Two public `live read-config` reads: 144 bytes, declared 144, CRC `0x2C40`,
10 fragments, **SHA-256 `bdef9c61…b895beb6`**, identical to each other and to the
historical baseline.

## Target

`armorx config map baseline.json M1=A -o target-m1-a.json`, validated with
`armorx config validate`. Exactly three bytes change:

| offset | before | after | meaning |
| --- | --- | --- | --- |
| 0 | 44 | 188 | CRC high byte |
| 1 | 64 | 77 | CRC low byte (`0x2C40` → `0xBC4D`) |
| 135 | 1 | 0 | `mapKeys[23]` (M1 source): B → A |

Undecoded changed bytes: **0**. Target SHA-256 **`e91ee3d0…183e61c1`**.

## Public apply

**Dry run** — status `DRY_RUN`, stopped at the confirmation stage, two identical
live reads, backup trio written, backup reopened and SHA-verified against the
live image, diff recorded, `mutating_frames_sent: 0`, `allow_mutating` never
enabled, backup bytes equal to the manually captured baseline.

**Confirmation** — the public confirmation abstraction presented the change with
`kdialog` (title "ARMOR-X configuration change", buttons APPLY / Cancel) and the
dialog was verified on screen before the click. It listed the model, the
firmware, both SHA-256 values, the changed-byte count, the decoded
`mapKeys[23]: B -> A` change, `undecoded changed bytes: 0` and the backup file
name. The operator clicked APPLY.

**Result** — `APPLIED`.

| step | observed |
| --- | --- |
| D7 | 10 fragments, indexes 1–10, nine 15-byte + one 9-byte data fragment, all checksums valid, 101 ms |
| D7 acknowledgement | `a5 05 d7 00 81`, observed once |
| 0E | `a5 05 0e 00 b8` sent exactly once → two identical notifications |
| D6 #1 | 144 bytes, CRC `0xBC4D` valid, SHA `e91ee3d0…`, state `TARGET` |
| D6 #2 | identical; both reads byte-for-byte equal to the target |

The connect step retried once (2 attempts) and both retries happened before the
first mutating frame.

## Physical effect

A passive usbmon capture was started **before** the operator action. The
controller exposes itself as an Xbox GIP device (`045e:0b12`) and the capture
holds 11 980 type-`0x20` 48-byte reports from it. At the single M1 press the
button byte went `0x01 → 0x11 → 0x01`: **bit `0x10` (A) set, bit `0x20` (M1)
never observed** (0 of 11 980 reports). M1 now emits A on the wire, exactly the
mapping that was written.

The host evdev node for the controller is not readable by this user, so the
correlation rests on the wire — which is the decisive evidence in any case.

## Power-cycle persistence of the target

USB identity sequence `045e:0b12 → absent → 413d:2106 → 045e:0b12` while the
operator powered the controller off and on. The first read after the cycle was
`e91ee3d0…183e61c1` with a valid CRC: the public `apply` persisted the change.

## Public rollback

The rollback wrote back **the exact bytes of the saved `.bin`** — never an image
rebuilt from the decoded document (a unit test edits the `.json` to all zeros and
still gets the correct image back).

| step | observed |
| --- | --- |
| backup | `.json`/`.bin`/`.sha256` agree; SHA `bdef9c61…b895beb6`; 144 bytes; CRC `0x2C40` |
| dry run | `DRY_RUN`, 0 mutating frames |
| confirmation | `kdialog`, accepted |
| result | `RESTORED` |
| D7 | 10 fragments, acknowledgement `a5 05 d7 00 81` |
| 0E | `a5 05 0e 00 b8` once → two identical notifications |
| D6 #1 / #2 | both `bdef9c61…b895beb6`, state `BASELINE` |

This particular rollback also needed `--allow-unrelated-state`, because the
backup had been taken by the build that predates the fix below. The override is
the documented escape hatch and was recorded in the report.

## Final state

Power-cycled once more, then read: **SHA-256 `bdef9c61…b895beb6`**, 144 bytes,
CRC `0x2C40`, byte-for-byte identical to the original configuration.
**FINAL CONFIG == ORIGINAL: YES.**

## Product bug found, fixed and revalidated on hardware

**APPLY-ROLLBACK-PAIR-001.** The public `apply` never wrote the session record
that `rollback` reads, so a normal apply-then-rollback pair was refused with
`state_classification: "different"` unless `--allow-unrelated-state` was passed.
The experimental reversible path did write a record, which is why the pair had
never been exercised.

Fix: `apply` now records its intent — baseline SHA, target SHA, changed offsets,
the backup's base file name and the device model/firmware — **before** the D7
write, so an interrupted transaction is still rollbackable, and marks
`apply_verified` after a successful verification. `rollback` is unchanged and
still refuses a live image that is neither the backup nor the recorded target.
Five regression tests cover it.

Revalidated on hardware: a second apply→rollback cycle produced
`APPLIED` (record written, format `armorx-live-apply-session-v1`), then
`RESTORED` with `state_classification: known_target` and **no override**, leaving
the device at `bdef9c61…b895beb6` again.

## Report classification correction

Verification attempts used to be labelled against whatever image the caller
expected, so a read that correctly matched the *target* was reported as
`state: BASELINE`. Each attempt now carries `matches_expected` (the safety fact)
plus a `state` derived from the session's own images: the actual original image
is `BASELINE`, the intended new image is `TARGET`, anything else is `UNEXPECTED`.
Seven regression tests cover the public, rollback and experimental paths.

## Privacy

Every report, backup and metadata file produced by the public commands was
scanned: no BLE address, no user name, no host name, no home path, no serial, no
token. Backups record base file names only. Local `live scan` output does contain
addresses and stays in the local runtime directory; it is not committed.
