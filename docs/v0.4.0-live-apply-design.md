# Design: the public `armorx live apply` path (not implemented)

Status: **design only**. No `apply` / `write-config` command exists on this
branch, and a test fails if one is added. The reversible M1 -> A experiment
(`docs/v0.4.0-reversible-m1-validation-2026-09-29.md`) proved the write path on
real hardware: full-image D7, `0E` persistence, byte-for-byte `D6` verification,
durability across a power cycle, and a byte-exact restore. This document records
what a public command must inherit before it can be exposed.

## Command shape

```
armorx live apply <target.json|bin> --address <addr> [--dry-run] [--yes] [-o report.json]
```

The target is an ordinary configuration image the user supplies, so every guard
below is about making a user-supplied image safe to write.

## Mandatory pipeline (refuse at the first failed step)

1. **Connect and read identity.** Model and firmware are recorded in the report
   and shown in the confirmation step; a mismatched model is a hard refusal.
2. **Read the live image twice.** Both reads must be byte-identical; otherwise
   the device is changing underneath us and nothing is written.
3. **Validate the live image.** 144 bytes, declared length 144, CRC valid.
4. **Validate the target.** Same three checks, plus a refusal if the target's
   declared length is not 144, and a refusal if the target is byte-identical to
   the live image (nothing to do).
5. **Automatic pre-write backup.** Write `<prefix>.json`, `.bin`, `.sha256` for
   the *live* image before anything else, exactly as
   `validate-write-gate` and `validate-reversible-m1` do today. The report
   records base names only, never a path.
6. **Exact diff.** Print and record every differing offset with its before and
   after value, plus a decoded field-level summary where the format is known
   (mapKeys, DPI, lighting, macro slots). Unknown offsets are shown as raw bytes
   and marked undecoded rather than guessed.
7. **Explicit confirmation.** A dialog showing the exact byte count and the
   decoded changes; `--yes` alone is not enough. `--dry-run` stops here.
8. **Write the full 144-byte image** as ten D7 A4 fragments, recording index,
   data size, checksum and timestamp for each, and collecting a bounded window
   for the D7 acknowledgement. An absent acknowledgement is recorded as absent.
9. **Persist once.** Send `A5 05 0E 00 B8` exactly once and record every
   notification in a bounded window.
10. **Verify by `D6`.** Two reads, each requiring exact byte and SHA-256 equality
    with the target and zero differing offsets.
11. **Classify any mismatch** as BASELINE / TARGET / UNEXPECTED. BASELINE means
    nothing happened; TARGET is a spurious read; UNEXPECTED is a hard stop —
    alert, preserve every artifact, never write again automatically.
12. **Report** in the same shape as the existing commands, with a
    `status` of APPLIED / FAIL / REFUSED and no fabricated fields.

## Rollback support

The pre-write backup *is* the rollback image. A matching command:

```
armorx live rollback --backup-prefix <prefix> --address <addr>
```

reopens `<prefix>.bin`, refuses unless its SHA-256 matches the SHA recorded in
`<prefix>.json`, and then runs steps 8-11 against that image. The restore path
of `validate-reversible-m1` already implements exactly this behaviour: the saved
baseline is authoritative, and a tampered file is refused.

## What must not happen

- No raw opcode console and no arbitrary-payload command.
- No write without a backup that has been flushed to disk and its SHA reread.
- No automatic retry loop that alternates D7 and 0E.
- No blind overwrite of an unrecognised third configuration state.
- No pairing, no firmware or OTA traffic, no interaction with `BUpgrade.exe`.

## Open questions before exposing `apply`

- Which fields are decodable enough to show in a confirmation dialog? The
  144-byte format is only partly reversed; unknown regions must be presented as
  opaque bytes with a warning.
- Should a target be constrained to a "patch" that names fields, so a whole
  user-supplied image is impossible? The reversible experiment argues for the
  patch shape: the one safe mutation we have proven was derived, not supplied.
- Does `0E` need to be repeated for devices that do not acknowledge it? Today's
  evidence is one frame, two notifications, and no retry.
