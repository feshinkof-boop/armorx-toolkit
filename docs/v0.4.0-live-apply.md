# Linux BLE configuration writes: `armorx live apply` and `live rollback`

**Release:** v0.4.0. Linux BLE support is optional and uses Bleak. The Windows
application remains a separate deliverable; nothing here replaces it.

These two commands write to the controller over BLE. They reuse the protocol
primitives that were proved on real hardware in
`docs/v0.4.0-reversible-m1-validation-2026-09-29.md`: a full 144-byte image as
ten D7 fragments, one `0E` persistence frame, and `D6` verification reads.

## The safety model

```
read live config twice  ->  refuse if they differ
validate (144 / declared 144 / CRC)
compare with the target ->  no changes? stop, no write
automatic pre-write backup (.json + .bin + .sha256)
reopen the backup and prove its SHA-256 equals the live image
diff every changed byte, and classify each one
refuse if any undecoded byte would change (unless explicitly allowed)
ask the operator, showing exactly what changes
D7 the target, once          ->  bounded window for the acknowledgement
0E once                      ->  bounded window for the notifications
D6 verify twice, both must equal the target exactly
```

At no point is an image rebuilt from decoded fields. `apply` writes the file you
gave it; `rollback` writes the bytes in the saved `.bin`, and refuses if the
three backup files disagree with each other.

## apply

```
armorx live apply target.json --address <BLE address>
armorx live apply target.bin  --address <BLE address>
armorx live apply target.json --address <BLE address> --dry-run
```

- `target` is a `.json` configuration or a 144-byte `.bin`; it is validated
  offline before anything is connected.
- the pre-write backup defaults to `<target>-backup-<local timestamp>`; use
  `--backup-prefix` to choose it.
- `--dry-run` connects, reads the live image twice, writes the backup, prints the
  plan and stops. It never enables the mutating gate, so `D7` and `0E` cannot be
  sent.
- no opcode, payload, fragment or raw-hex option exists. There is no console.

### Statuses

| status | meaning |
| --- | --- |
| `APPLIED` | written, persisted and verified byte-for-byte twice |
| `NO_CHANGE` | the device already holds that exact configuration |
| `DRY_RUN` | plan produced, nothing written |
| `REFUSED` | a guard said no; nothing was written |
| `FAIL` | the write or the verification did not complete as intended |
| `UNEXPECTED_STATE` | the device holds a configuration that is neither the baseline nor the target |

## Undecoded bytes

The 144-byte format is only partly reversed. A change to a byte that no
recovered field covers (the reserved ranges) is **refused by default**:

```
armorx live apply target.json --address ...     --allow-unknown-diff --acknowledge-backup
```

When the flag is used, every unknown offset is listed in the confirmation and in
the report. This is what protects a user from flashing a community
configuration that carries opaque state.

## rollback

```
armorx live rollback baseline-original --address <BLE address>
armorx live rollback baseline-original --address <BLE address> --dry-run
```

The prefix is the one used at apply time. All three files must exist and agree:
`.json`, `.bin` and `.sha256`. The live configuration is then classified:

- identical to the backup → `NO_CHANGE`, nothing written;
- equal to the target recorded in `<prefix>.session.json` → the rollback is
  allowed;
- anything else → **refused** unless `--allow-unrelated-state` is given, and the
  operator is asked either way.

## Confirmation

By default the command asks the operator, showing the device model, firmware,
both SHA-256 values, the changed-byte count, the decoded changes, the undecoded
count and the backup file name:

- `kdialog` when it is installed and a desktop session is present;
- a terminal prompt otherwise, when stdin is interactive;
- a refusal in a non-interactive run.

Automation is deliberately two switches, not one:

```
armorx live apply target.json --address ... --yes --acknowledge-backup
```

`--yes` alone is refused with a message. The same applies to `rollback`.

## Connections

The connect step retries a bounded number of times (`--connect-attempts`,
default 3). Retrying is only ever possible **before** the first mutating frame: a
connection lost mid-write is answered by a read-only `D6` classification, never
by re-sending the transaction. There is no automatic retry loop and no silent
rollback.

## Privacy

Reports and backups never contain the BLE address, a serial number, a user name,
a host name, a home directory, an absolute backup path or a token. Backups record
file *names* only. Scan output shows addresses locally for connecting — do not
publish them in issue reports.
